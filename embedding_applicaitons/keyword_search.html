Keyword to Semantic Search

How does a search box decide which documents match "the cat"? We start with the simplest idea, find where it breaks, and fix it, three times.

TF → TF-IDF → BM25 → semantic search (second tab)

Our tiny corpus (N = 5 documents) used in every example below.

Query for the worked examples: the cat. Which document do you think should win?

1. Term Frequency (TF)

Idea: a document that mentions a word more often is probably more about that word. Score a document by counting query words in it.

tf(t, d) = number of times term t appears in document d score(q, d) = sum of tf(t, d) for every term t in the query q

Worked numeric example: query "the cat"

Flaw 1: every word counts equally.

"the" is in every document, so it tells us nothing, yet it adds the same weight as "cat". In the table, D2 ties with D3 mostly because of the word "the", although D3 is clearly the most "cat" document (3 cats, a cat-food page), and cat-less D4/D5 still get points.

Flaw 2: long documents win.

A long document has more chances to contain the words. Raw counts do not account for length. (A common patch, dividing by length, tf = count / len(d), helps a bit but still does not fix flaw 1.)

2. TF-IDF

Fix for flaw 1: weight each word by how rare it is across the corpus. A word found in every document is useless for telling documents apart; a word found in one document is a strong signal.

df(t) = number of documents that contain t idf(t) = ln( N / df(t) ) tfidf(t,d) = tf(t, d) x idf(t) score(q,d) = sum of tfidf(t, d) over query terms

Step 1: inverse document frequency (N = 5)

"the" appears in all 5 documents so idf = ln(5/5) = 0. It is switched off automatically. "cat" appears in 3 of 5.

Step 2: multiply tf by idf

Flaw 1: tf grows linearly (keyword stuffing).

10 mentions of "cat" is scored 10x a single mention. But a document that says "cat" 100 times is not 100x more relevant. Spammers exploit this. Real relevance saturates.

Flaw 2: no length normalisation.

A 1,000-word article containing "cat" 3 times scores the same as a 5-word note with 3 cats, even though the short note is far more focused.

Flaw 3: edge cases.

If a term is in every document, idf is exactly 0 (fine). With other formulas idf can even go negative. We need a safer, smoother idf.

3. BM25 (Okapi BM25)

Fix: keep the idf idea, but make tf saturate and normalise for document length. This is the algorithm behind Lucene, Elasticsearch and many production search engines.

idf(t) = ln( (N - df + 0.5) / (df + 0.5) + 1 ) # always >= 0 tf x (k1 + 1) tfpart = ------------------------------------ tf + k1 x (1 - b + b x len(d)/avgdl) score(q,d) = sum over query terms of idf(t) x tfpart
Two knobs
  • k1 (typically 1.2 to 2.0) controls saturation. Small k1: after a couple of mentions extra ones barely help. Large k1: closer to linear TF.
  • b (0 to 1, typically 0.75) controls length normalisation. b=0: ignore length. b=1: full normalisation against the average document length (avgdl).

Play with the knobs

x-axis: how many times the word appears (0 to 30) in a document of average length. y-axis: score contribution. Grey dashed = raw TF/TF-IDF (straight line, no limit). Blue = BM25 flattens out. Orange = same word count in a document twice as long as average: it is penalised when b > 0.

Worked numeric example: query "the cat"

What BM25 still cannot do.

It only matches exact words. Search "automobile" and a document about a "car" scores zero. "feline" will not find "cat". It has no idea that words have meanings. That is why we need embeddings and semantic search, the next lesson.

Semantic Search: search by meaning

Keyword search asks "do the same words appear?". Semantic search asks "do the same ideas appear?". The trick: turn text into numbers that capture meaning.

The problem we are solving

Search feline in our corpus. BM25 gives every document a score of 0 because the word "feline" never appears, even though three documents are about cats. Try it:

1. What is an embedding (vector)?

An embedding is a list of numbers (a vector) that represents a piece of text so that similar meaning → similar numbers. A neural network learned these numbers by reading huge amounts of text.

"cat" -> [ 0.90, 0.10, 0.00, 0.00 ] "feline" -> [ 0.95, 0.05, 0.00, 0.00 ] close to "cat" "dog" -> [ 0.10, 0.90, 0.00, 0.00 ] different direction "pizza" -> [ 0.00, 0.00, 0.90, 0.00 ] very different
Think of it as coordinates on a map of meaning. Each position (dimension) is some learned feature. In our toy example the 4 dimensions are roughly cat-ness, dog-ness, food-ness, vehicle-ness. We chose these by hand so you can read them.
  • Real models: dimensions are not human-readable. all-MiniLM-L6-v2 gives 384 numbers per sentence; OpenAI text-embedding-3-small gives 1536.
  • A sentence/document vector represents the whole text. In our toy we simply average the word vectors. Real models use a transformer that reads the whole sentence in context.
  • Same model must embed both documents and queries, otherwise the numbers are not comparable.

Toy map of meaning (2 of the 4 dimensions)

x = cat-ness, y = dog-ness. Words with similar meaning sit near each other, and point in the same direction from the origin.

2. Cosine similarity: how close are two vectors?

We need one number saying "how similar are these two vectors?". The standard choice is the angle between them.

A . B sum(Ai x Bi) cos(A, B) = --------------- = ------------------------------- |A| x |B| sqrt(sum Ai^2) x sqrt(sum Bi^2)
  • 1 = same direction (same meaning)   0 = unrelated (90°)   -1 = opposite
  • It ignores vector length, so a long document and a short one about the same topic can still match.
  • If vectors are normalised to length 1, cosine is just the dot product. That is why vector databases are fast.

3. Vector database

With 5 documents you can compare the query against all of them. With 50 million you cannot. A vector database stores vectors and finds the nearest ones quickly.

What it stores
id | vector (e.g. 384 floats) | metadata / original text D1 | [0.9, 0.1, 0.0, 0.0, ...] | "the cat sat on the mat" D2 | [0.4, 0.5, 0.0, 0.0, ...] | "the dog chased the cat in the garden" ...
What it does
  • Exact search (brute force): compute cosine with every vector, sort. Perfect but O(N). Fine up to ~100k vectors.
  • Approximate Nearest Neighbour (ANN) search: build an index (HNSW graphs, IVF clusters, product quantisation) so you check only a small fraction of vectors. Slightly less accurate, vastly faster.
  • Examples: FAISS (library), Chroma (simple, local), pgvector (Postgres extension), Qdrant, Pinecone, Weaviate. MongoDB Atlas also has vector search.
  • Also handles inserts/deletes, persistence, and filtering ("only docs from 2024").

4. A simple query, step by step

  1. Index time (once): embed every document → store vectors in the vector DB.
  2. Query time: embed the query with the same model.
  3. Compare: cosine similarity between the query vector and every stored vector (or ANN lookup).
  4. Rank: sort by similarity, return the top-k.
query = "feline" q_vec = embed(query) # [0.95, 0.05, 0, 0] scores = [cosine(q_vec, v) for v in db] # one score per document top_k = sorted(by score, descending)[:3]

In real Python this is about 5 lines with sentence-transformers:

from sentence_transformers import SentenceTransformer model = SentenceTransformer("all-MiniLM-L6-v2") doc_vecs = model.encode(docs, normalize_embeddings=True) # index time q_vec = model.encode("feline", normalize_embeddings=True) scores = doc_vecs @ q_vec # cosine (vectors are normalised) top = scores.argsort()[::-1][:3]
